# XDev

**让“完成了”成为可以核对的结论。**

为 Codex 的 AI 开发流程提供工程治理与交付证据。

[English](README.md) · **简体中文**

[快速开始](#快速开始) · [社区操作说明](docs/COMMUNITY.md) · [X Suite](https://github.com/NUVANU/X-Suite)

AI 可以写出代码，也可以很自信地告诉你完成了。更难回答的是：是否遵守约定范围？有人审查过实际改动吗？QA 测的是否就是你将收到的候选版本？

**XDev 将这些问题对应到具体项目的记录。**准备已经批准的工作，核对输入与范围绑定，分别记录实施、Review、实际 QA 和交付结果。编码与 Agent 执行，仍由宿主和模型完成。

## 为什么使用 XDev？

| 常见问题 | XDev 增加的核对 |
| --- | --- |
| 输入还含糊，或已经被替换，就开始执行 | 针对已批准、版本化输入做准备与预检 |
| 文件同名，却来自其他项目或旧版本 | 明确的项目映射、文件引用与内容哈希 |
| Agent 增加了需求以外的功能 | 批准/禁止范围，以及 Review 符合性核对 |
| “审查过”与“测过”对应不同候选 | 让阶段证据共同绑定 Job 与候选版本 |
| 把实施者自检当成独立 QA | 区分实施、Review、实际 QA 各自所需的证据 |
| 断连后不知道最后一次 QA 的结果 | 先只读诊断，再按原记录进行有界对账恢复 |

适合原型开始转向持续维护、多 Agent 需要交接，或希望查看交付依据而不只依赖最后一句回复的项目。

## 开发流程是什么样？

```text
确认过的请求与允许范围
          ↓
Prepare → Preflight → Start Job
          ↓
实施 → Review → 实际 QA
          ↓
带相关证据的状态与结果
```

流程通过宿主支持的工具和 XDev 结构化接口完成。某阶段成功不会授予额外权限，接收到规格也不等于允许开始开发。

### 1. 核对正确的项目与输入

`xdev_context` 展示实际绑定项目、配置与可用权限；`xdev_prepare`、`xdev_preflight` 在启动 Job 前核对支持的来源和绑定条件。未绑定的 MCP 服务只提供 context，不会静默将工作目录当作项目。

接收 XMi 规格时，将 XSpec 身份明确映射到选定的 XDev 项目，核对 manifest 与原文件，并提供回读回执。普通任务也可以从清楚且已确认的请求开始，不要求每次改动都使用 XMi。

### 2. 让开发与验证证据对应起来

实施、Review、QA 和交付记录使用同一 Job 与批准版本。公开工作流支持不同保证档位；正式完整治理要求实施、Review、QA 使用不同会话。原型自检保留其有限状态。

例如修改取消规则，应核对已约定行为、实际 diff，以及该候选的 QA 回执，不能借用旧文件集合上的通过结果。

### 3. 中断后先对账，再继续

状态与结果查询读取原 Job，不派发额外工作。QA 已执行落盘、但最终登记缺失时，文档所述恢复路径要求找到原结果并具备对应恢复许可。结果未知不能成为擦除证据、盲目重跑 QA 的理由。

## 快速开始

当前公开源码：**V0.1 社区版系列 · 包版本 `0.1.2` · MPL-2.0**，文档所述联合安装配套 **XMem `0.1.1`**。

**安装和项目配置请按 [X Suite Windows 指南](https://github.com/NUVANU/X-Suite/blob/main/INSTALL.md) 操作。**其中包括配套 XMem 运行目录、部署清单、XDev 本地插件和明确的项目绑定。

源码准备使用文档所述 **Node.js 24.20.0**、**pnpm 11.25.0**、**npm 11.19.0**：

```powershell
# 在 XDev 仓库根目录执行。
pnpm.cmd install --frozen-lockfile --ignore-scripts
npm.cmd --prefix mcp ci --ignore-scripts
npm.cmd run typecheck
```

源码 MCP 入口：

```text
node --experimental-strip-types <XDev绝对路径>/mcp/server.ts
```

单独启动服务不等于完成项目配置。按 [安装指南](https://github.com/NUVANU/X-Suite/blob/main/INSTALL.md) 设置后重建连接，用 `xdev_context` 核对。项目写入、QA 执行、规格接收和记忆操作分别判断权限。

**配置就绪且取得所需任务批准后**，可以这样提出请求：

```text
本项目使用 XDev，先核对项目绑定。
围绕已确认验收条件，在批准范围内开发。
分别保留实施、独立 Review 和实际 QA 的证据。
如实报告最终候选与尚缺的证据。
```

## 技术特点

| 机制 | 作用 |
| --- | --- |
| MCP + Skills + 源码 CLI | 提供结构化操作，引导支持的宿主流程 |
| 版本化准备/请求记录 | 明确批准输入与任务合同 |
| FileRef + SHA-256 + 候选清单 | 识别内容漂移，让证据对应具体字节 |
| Job 与阶段记录 | 区分实施、Review、QA 和交付声明 |
| 有界 Node QA 执行器 | 运行冻结的支持命令，保存真实回执 |
| 恢复与状态入口 | 核对中断工作，不把查询当成执行 |
| XMem 协作 | 显式读取与保存适用的项目知识 |

仓库还保留 `material-tools` 下的 PowerShell 材料准备工具，支持入口见 [社区操作说明](docs/COMMUNITY.md)。

哈希证明内容一致性，不证明审查意见正确，也不认证审查者的原生身份。文档所述监督路径的公开角色来源由协调者转交；独立会话和真实执行回执仍然必要。

## XDev、宿主与 XMem 的分工

- **宿主/模型：**编码、调用工具、调度 Agent、执行权限与生命周期。
- **XDev：**任务与范围绑定、证据要求、阶段记录、交付判断及有界恢复。
- **XMem：**持久保存工程历史、来源、修订与检索。
- **需要时使用 XMi：**澄清产品并导出规格。

XMem 历史是参考上下文，不是执行新任务的授权。XDev 不充当操作系统沙箱，也不会拦截任意 Shell 操作。

## 当前范围与限制

本 README 描述仓库已公开源码，不代表更新的本地开发构建。文档所述验收范围是本地 D2/联合流程；历史 D1 路径还有特定环境要求。

当前 MCP QA 路径支持精确 **Node.js 24.19.0 / 24.20.0**、**一条冻结命令**及**最多 90 秒同步 QA 预算**。不代表浏览器/UI、游戏引擎、负载或生产验收。断连或超时也不证明操作已经停止。

工具可见、安装成功、项目绑定、Job 完成、实际 QA 和发布验收分别成立。其他宿主与新电脑安装需要分别验证；本仓库不声明已测得某个缺陷降低比例。
