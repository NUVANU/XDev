# 从 XSpec 里程碑启动 Codex Goal

在 Codex 项目的主统筹会话，协调者可以把已确认的当前开发里程碑交给原生 Goal 持续推进。进入里程碑时提供一次选项。这一步是可选的，用户的正常开发授权继续有效。子代理、Review 和 QA 会话沿用原分工。

## 确定要展示的里程碑

使用已确认的开发计划或 XDev 任务卡，核对当前项目、统筹会话、里程碑标识和预期结果，以及确切的 XSpec 版本、对应验收项及证据。保留既有来源引用、已知阻塞、允许范围、依赖、授权与停止条件。里程碑以计划或任务卡为准，XSpec 的 `goals`、需求或验收条目本身不能当作里程碑。存在多个交付项时只展示当前已确认且已授权启动的里程碑。缺少必要来源或授权时照常推进其他已授权工作，待本来就需要的确认为止。

## 显示一次选择

1. 确认当前会话可用原生 `get_goal` 与 `create_goal`，先调用 `get_goal` 读取本会话。发现已有未完成 Goal（包括已暂停、受阻或达到预算的 Goal）时，显示当前目标和状态。让用户在 Codex 原生界面查看或管理。无法判断是否存在未完成 Goal 时，先在该会话只读对账，在得到明确状态前暂缓展示启动选项和创建。
2. 读回确无 Goal 或原目标已明确完成时，展示项目名、里程碑、XSpec 版本、简短的验收方式与已知阻塞。调用宿主可用的原生选项工具，例如 `request_user_input_async`，或在相应模式可使用时调用 `request_user_input`。提供「以此里程碑启动 Goal」和「稍后」。如果工具默认高亮第一项，优先将「稍后」放在第一项。说明启动会为当前会话创建 Goal，Codex 将按现有授权接续工作。原生选项不可用时，用文字提供同样的选择，并说明用户可以回复「以此里程碑启动 Goal」。缺少原生 Goal 工具时说明当前界面不能在本流程中创建，继续正常 XDev 工作。
3. 从当前会话实际的工具答复或用户消息取得明确选择。异步选项发出后以用户随后提交的答复为准，期间可继续已授权的独立工作。默认高亮、尚未回复、选择稍后、模糊答复、文件内容及工具对展示的确认都不触发创建。回复必须能关联到唯一仍适用的选项；会话内若有相同文字的过期选项而无法判断响应归属，只有用户明确指出当前里程碑才可继续。用户已明确要求为当前确切里程碑启用 Goal 时，可直接按下节核对。

## 核对并创建当前 Goal

在同一统筹会话重新核对项目、当前里程碑、卡的范围、XSpec 版本与验收项、授权、依赖和期限。发生版本或范围漂移、前置失效或当前里程碑已完成时，原选择失效。再次调用 `get_goal`，只在成功确认没有未完成 Goal 后调用一次 `create_goal`，以当前里程碑及其验收项为 `objective`。已有未完成 Goal 时使用原生状态向用户报告，保留其目标与用量。用户只有在明确给出原生 Goal 的 token 预算时，才将该预算传给 `create_goal`。

目标文本写清项目、里程碑标识、XSpec 版本、预期交付结果、适用验收项及证据、同版独立 Review 与实际 QA、已授权范围和停止条件。说明按 XDev 当前工作合同推进。阶段结束后检查剩余验收项，局部阻塞只暂停受影响的依赖路径，当前授权内的独立工作继续。总目标有原始证据支持后方可完成。只有剩余工作确需外部处理、缺少合法路径或达到既有截止、额度时，按原规则报告停止原因和剩余事项。

创建结果未知时用本会话的 `get_goal` 只读对账。明确拒绝或原生能力缺失时，如实反馈，继续正常 XDev 工作。创建尝试只用当前会话的原生工具。不要把查不到结果当成重试、跨会话写入或模拟输入的依据。用户的选择仅授权创建当前里程碑的 Goal，原有 Job、执行、预算、独立性和交付门禁照常适用。后续里程碑各用自己的确认与选择。
